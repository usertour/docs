## Introduction

Usertour.js is a lightweight client-side SDK that enables you to:
- Identify and track users in your web application
- Display interactive content (flows) to your users
- Collect user behavior data for targeting

[Follow us on Twitter](https://x.com/usertourio) for the latest updates and announcements.

## Core Methods

Here are the most commonly used methods:

| Method | Description |
| ------------------------------ | ------------------------------------------- |
| [usertour.init()](/developers/usertourjs-reference/setup/init) | Initialize the SDK with your Usertour.js Token |
| [usertour.identify()](/developers/usertourjs-reference/users/identify) | Identify and track a user |
| [usertour.group()](/developers/usertourjs-reference/companies/company) | Associate a user with a company/group |
| [usertour.track()](/developers/usertourjs-reference/events/track) | Record a custom event for the current user |

## Installation

### Recommended: NPM Installation

We recommend using the npm package for the best development experience:

```bash
# Using npm
npm install usertour.js

# Or using Yarn
yarn add usertour.js
```

For alternative installation methods, see [Usertour.js Installation Guide](/developers/usertourjs-reference/installation).

<Note>
If you're using a self-hosted UserTour instance, you'll need additional configuration to connect Usertour.js to your own server. See our [Self-Hosted Usertour.js Guide](/open-source/usertourjs) for detailed setup instructions.
</Note>

## Quick Start

Add this code to your application where you have access to user information:

```javascript
import usertour from 'usertour.js';

// Initialize with your Usertour.js Token
usertour.init('<USERTOUR_TOKEN>');

// Identify the current user
usertour.identify('<USER_ID>', {
  name: '<NAME>',
  email: '<EMAIL>',
  signed_up_at: '2023-06-14T16:25:49Z',
});
```

### Important Notes

#### Replace Placeholders
- Replace all placeholders (e.g., `<USERTOUR_TOKEN>`, `<USER_ID>`, `<NAME>`, `<EMAIL>`) with your actual values
- The `signed_up_at` timestamp should be in ISO 8601 format

#### Getting Your Token
- Find your Usertour.js Token in Settings -> Environments
- Each environment (Production, Staging, etc.) has its own unique token
- Make sure to use the correct token for your environment

## How It Works

The npm package (`usertour.js`) is a thin wrapper around the real Usertour.js, which is loaded from our CDN. This design allows you to interact with the imported usertour object immediately. When you make your first method call, the real Usertour.js will be automatically loaded (asynchronously) and injected into the current page. All method calls are automatically queued by the usertour object until the SDK is ready.

The core SDK is optimized for performance:
- Small footprint (less than 16 KB gzipped)
- Loads UI components only when needed
- Supports both modern and legacy browsers

If you've installed Usertour.js via a `<script>` tag, you can access the object via `window.usertour`. However, be aware that it may not be immediately available, which is why we recommend using the npm package.

## Attributes

The SDK provides a flexible attribute system for storing data about various entities like users, companies, and events. You can use this to store a user's name, a company's plan type, or decorate events with information like which billing plan was selected. These attributes can then be used within Usertour to segment users, personalize flows, or track behavior.

When updating objects with attributes, you can use various data types:

| Type | Description | Example | Common Use |
|:---|:---|:---|:---|
| **string** | Text values | `"John Doe"` | Names, emails |
| **number** | Numeric values | `42` or `1234.56` | Scores, metrics |
| **boolean** | True/false values | `true` or `false` | Feature flags |
| **datetime** | ISO 8601 timestamps | `"2023-06-14T16:25:49Z"` | Event times |
| **list** | Arrays of strings | `["tag1", "tag2"]` | Tags, categories |

Here's how to use attributes in your code:

```javascript
// Set user attributes
usertour.identify('123456', {
  name: 'John Doe',
  is_premium: true,
  subscription_tier: 'pro',
  last_login: '2023-06-14T16:25:49Z',
  tags: ['beta', 'early-adopter']
});

// Set company attributes
usertour.group('company_123', {
  name: 'Acme Corp',
  plan: 'enterprise',
  employee_count: 500,
  industry: 'technology'
});

// Remove an attribute by setting it to null
usertour.updateUser({
  phone_number: null
});
```

A `Date` object is sent as an ISO 8601 UTC timestamp, so `signed_up_at: new Date(user.createdAt)` is the simplest way to store a datetime.

### Attribute types

Every attribute has a definition with a type. The first value you send for a new attribute creates the definition and decides its type — a string is stored as **datetime** only in the strict `2024-12-12T00:00:00.000Z` form (what `Date.prototype.toISOString()` produces), otherwise as **string**. Once a definition exists, later values must fit its type; conversions that lose nothing are applied for you, anything else is dropped (the SDK logs a warning) or rejected (the REST API returns 400):

| Definition type | Accepted values |
|:---|:---|
| **string** | Any string; numbers and booleans are stored as strings |
| **number** | Numbers; a numeric string such as `"42"` when it converts exactly (`"007"` does not) |
| **boolean** | Booleans; the strings `"true"` and `"false"` |
| **datetime** | Any ISO 8601 date-time with a zone, normalized to UTC (`2024-12-12T08:30:00+08:00` becomes `2024-12-12T00:30:00.000Z`). Date-only strings and epoch numbers are not accepted |
| **list** | Arrays of strings, numbers or booleans; a single value becomes a one-element list |

You can change a definition's type later in **Settings → Attributes**, as long as no stored value conflicts with the new type.

### Operations

Instead of a literal, an attribute value can be an object with exactly one operation. Operations are computed on the server, so they work even though the browser never sees the stored value:

| Operation | Description |
|:---|:---|
| `{ set: value }` | Sets the value — the same as a literal, but lets you add `data_type` |
| `{ set_once: value }` | Sets the value only if the attribute has no value yet. Works again after the attribute was removed |
| `{ add: number }` | Adds to a **number** attribute; use a negative number to subtract. A missing attribute starts at 0 |
| `{ union: value \| [values] }` | Adds the values not already present to a **list** attribute. A missing attribute starts as an empty list |
| `{ remove: value \| [values] }` | Removes every matching value from a **list** attribute. A missing attribute stays undefined |

```javascript
usertour.updateUser({
  signup_source: { set_once: 'google' },
  widget_count: { add: 1 },
  days_left: { add: -1 },
  features_used: { union: ['export', 'share'] },
  beta_flags: { remove: 'old_ui' }
});
```

`add` is not idempotent: if a request is retried after the server already applied it, the value is added twice. For exact counts, track an event instead — conditions can match on how many times an event occurred, optionally within a time window.

### Pinning the type with `data_type`

When the first value of a new attribute could be misread — a string that happens to look like a date, a phone number sent as a number — pin the type with `data_type` next to `set` or `set_once`. The value is converted to that type:

```javascript
usertour.identify('123456', {
  // Stored as a string, even though the value looks like a datetime
  external_ref: { set: '2024-12-12T00:00:00.000Z', data_type: 'string' },
  // Stored as "12345678"
  phone: { set: 12345678, data_type: 'string' }
});
```

`data_type` only decides the type when the attribute is first created. It never changes an existing definition: a `data_type` that disagrees with the definition is treated as a type mismatch. Change the type in **Settings → Attributes** instead.

Event attributes accept literals, `Date` objects and `{ set, data_type }` only. The same values and operations work through the [REST API](/api-reference-v2/introduction) and the MCP server.

For best results, we recommend:
- Using consistent naming conventions (lowercase with underscores)
- Choosing appropriate data types for each attribute
- Avoiding storage of sensitive information
